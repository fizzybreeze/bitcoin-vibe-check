## Definition of done

All four must pass before pushing. `/verify` runs them in one go.

| Gate | Expectation |
|---|---|
| `npm run lint` | zero errors — the config is clean, so any error is new |
| `npm test` | all green |
| `npm run build` | succeeds |
| `npm run test:e2e` | all green — required for any UI change. Runs the behavioural specs twice, desktop and mobile, plus the `visual` pixel-comparison project; `--project=mobile` narrows it while iterating |
| `npm run test:smoke` | **not** part of the pre-push gates — it hits the deployed site, so it can only be meaningful after a merge. Run it (or the `smoke.yml` dispatch) when you want to confirm production is actually healthy |

Rules that hold regardless:

- **Never push to `main`.** It is protected; open a PR from a `claude/*` branch.
  CI (`Lint, test, build` + `Playwright (chromium)`) must pass before merge.
- **Re-check your base before opening a PR.** A long session can outlive the
  `main` it branched from. Run `git fetch origin main && git log --oneline
  HEAD..origin/main`; if that prints anything, rebase and re-run the gates — a
  clean rebase does not mean the combination still works. Then check
  `git diff --stat origin/main HEAD`: a file showing **pure deletions you did not
  intend** means you are about to revert merged work. PR #12 nearly reverted six
  PRs this way, with auto-merge already enabled.
- **The "Allow auto-merge" repository setting stays off. Permanently. This is
  settled — do not raise it.** Not as a simplification, not as a question, not
  as a "worth considering". A PR that merges the moment CI goes green races the
  human to production and makes the Vercel preview URL pointless: CI proves the
  code is *correct*, not that the change *looks right*, and on a visual product
  those are different questions. The setting is repo-wide, so enabling it for
  one purpose arms it for every PR in the repo — which is why the answer is no
  even when the immediate use looks narrow.

  **Unattended merging is a separate question, and it is already answered.**
  Dependabot PRs of type `semver-patch` or `semver-minor` merge themselves via
  `dependabot-auto-merge.yml`; majors and every human or `claude/*` PR wait for
  a person. That exception was asked for in #21 and is implemented *without*
  the repository setting — the workflow polls the two required checks and then
  merges, so branch protection stays the enforcer and the feature stays
  unavailable to everything else.

  **If some future change needs a PR to merge unattended, copy that pattern**
  — poll the required checks, then merge, scoped by an `if:` to exactly the
  PRs that qualify. That is the whole reason the pattern exists, and it means
  there is never a case where the repository setting is the answer. So there is
  nothing left to ask about here.
- **If production is broken, promote the previous build before reverting.**
  Vercel's rollback re-points traffic at a build that already exists, so it takes
  seconds; `git revert` and push waits for CI and a fresh build. The procedure
  lives in `README.md` → Deployment → *If production breaks*, and `/rollback`
  finds the target and reports the direct link. It reports only — pressing the
  button is the user's call.
- **Every behaviour change needs a test.** The fast unit suite is what makes it
  safe to review on a phone without reading the whole diff.
- **Never silence a gate to go green.** Deleting an assertion or adding a blanket
  `eslint-disable` turns a real signal into a silent one. A targeted disable is
  acceptable only when the rule is genuinely wrong there, and must carry a
  comment explaining why.
- **Any database change is a migration** in `supabase/migrations/`, never an
  ad-hoc dashboard edit. Re-run the Supabase security advisors after schema
  changes — they should stay at zero lints.
- **Never commit secrets.** `.env` is gitignored; `.env.example` documents the
  shape. This repo is public.

### Data flow

On mount, `loadData()` fires parallel API calls via `Promise.allSettled`:
- **CoinPaprika** — BTC price (USD/GBP/EUR/CAD/CHF), 24h volume, market cap, dominance
- **Kraken REST** — price ticker (seeds the values the WebSocket then keeps live)
- **mempool.space** — fee tiers, block height, difficulty adjustment, mempool stats, recent blocks, hash rate, Lightning stats
- **alternative.me** — Fear & Greed index (single `?limit=30` call serves both the current value and the sparkline)
- **`/api/chain-data`** — own serverless route, proxying BGeometrics MVRV
- **Kraken OHLC** — 200 daily candles for the 200-day MA and Mayer Multiple

After `loadData()` resolves, results are merged with `localStorage` (key `btc-cache`). The cache write is partial — only non-null fields overwrite stored values. Volume history (last 7 days) is tracked separately under `btc-vol-history`.

Prices are then kept live via a **Kraken WebSocket v2** connection (`wss://ws.kraken.com/v2`), subscribing to the `ticker` channel for BTC/USD, BTC/GBP, BTC/EUR, BTC/CAD, BTC/CHF. The rest of the KPI data refreshes on a 60-second `setInterval`.

Chart data (`fetchChart`) comes from **Kraken OHLC** via `src/lib/ohlc.js`, with the interval derived from the selected range (1D → 60min/24 candles, 7D → 240min/42, 1M → 1440min/30, 1Y → 1440min/365). Kraken has no `limit` parameter and returns up to 720 candles, so the app slices client-side. Fetched charts are memoised for the session by `src/lib/chartCache.js`, keyed by range. All four ranges are warmed by a mount-time effect; `startBackgroundPrefetch` warms the other three again after the active range loads, which on a healthy cold load finds them already there and is really the recovery path for a mount prefetch that failed. The two paths do not race, because the store is consulted when a request is *made* rather than when it is scheduled — see v1.7.2 below.

> **CoinGecko is no longer used.** It was replaced by CoinPaprika (market data) and Kraken (charts). The vestigial CoinGecko mocks were removed from `e2e/dashboard.spec.js`.
>
> Two dead references outlived the switch and were removed in v1.4.5: a Workbox
> `runtimeCaching` rule for `api.coingecko.com` in `vite.config.js`, and
> `VITE_COINGECKO_API_KEY` in `ci.yml`'s build step. The caching rule is the
> instructive one — while it sat there caching a host the app never called,
> CoinPaprika, Kraken and `/api/chain-data` had **no** rule, so the PWA was
> dropping exactly the data it existed to keep. `pwaRuntimeCaching.test.js` now
> pins the rule set to the External APIs table below.

### The Vibe Score

`computeVibeScore` in `src/lib/calculations.js`. A pure function over data the
dashboard already fetched — no network call, no new dependency, no new
`runtimeCaching` rule.

| Dimension | Input | Anchors (clamped) | Weight |
|---|---|---|---|
| Sentiment | Fear & Greed | 0–100 direct | 30% |
| Valuation | mean of Mayer Multiple and MVRV | Mayer 0.8 → 2.4; MVRV 1.0 → 3.7 | 30% |
| Momentum | 30-day price change from the 200-day candle series | −25% → +25% | 25% |
| Congestion | mean of fastest fee tier and mempool pressure | log₁₀ 1 → 100 sat/vB; 0 → 200k txs | 10% |
| Network | 30-day hash-rate trend | −10% → +15% | 5% |

Three rules that are load-bearing, not stylistic:

- **Single polarity.** Every dimension is scaled so higher means hotter. The
  roadmap originally proposed a contrarian valuation dimension inside an
  otherwise pro-cyclical composite; scored against five historical market
  states that version spanned only 38–72 and read the December 2022 bottom as
  45 — "slightly below neutral". Single polarity spans 8–76 on the same inputs.
  It also keeps the number descriptive: a score where *cheap* pushes the value
  up is a buy signal by another name, and signals are in §7's not-doing list.
- **Momentum is not the Mayer Multiple.** Mayer *is* price ÷ 200-day MA, so
  sourcing momentum from the same ratio would have put 35% of the score on one
  number. It reads 30-day price change instead, off candles already in memory.
- **Degrade, never vanish.** A missing input drops its dimension and the rest
  renormalise — MVRV rides a 15-request/day free tier and will be absent
  sometimes. Below 3 dimensions or 0.6 of the weight the function returns
  `null` and the card says so rather than inventing a number.

The header sentence comes from `computeVibeSummary`, over the same dimension
values, naming the three furthest from neutral. Deriving both from one source is
what stops the words and the number contradicting each other on screen.

> **The weights are not calibrated against anything.** `metric_snapshots` held 2
> rows when this shipped, so there was no history to fit them to. They are
> chosen for legibility and live in `VIBE_WEIGHTS`/`VIBE_ANCHORS` so they are
> cheap to revise. If the score is ever persisted, persist the *inputs* and
> recompute — storing the score itself puts a permanent discontinuity in the
> series at every weight change.
>
> As of v1.6.4 the snapshot row carries **all seven** inputs, so any stored day
> replays into the score the card showed. Use `vibeInputsFromMetrics()` for the
> mapping and let `snapshotMetrics.test.js` keep it sufficient. Rows captured
> 4–6 Aug 2026 predate `price_change_30d_pct` and have no momentum dimension —
> they will score slightly differently from how they read on the day.
>
> v1.6.9 is the first consumer of that replay. `src/lib/vibeHistory.js` plots a
> row **only** when `inputsUsed === inputsTotal`, so those three rows drop out
> on their own rather than being labelled. Degrading is right for the live card
> and wrong for a series: the whole claim a line makes is that its points are
> comparable, and a renormalised point is a weight change drawn as a movement.
> An eighth input added without a snapshot field will shorten the sparkline
> rather than skew it — which is the loud failure this arrangement is for.

### Visual regression

`e2e/visual.spec.js`, in its own `visual` Playwright project. Covers the failure
mode nothing else does: a Tailwind class change that wrecks the mobile layout
passes every text assertion in the suite *and* is invisible in a diff on a
phone, so both review paths are blind at once.

Four cards are snapshotted — Cycle Indicators, Network Pulse, BTC Price, Recent
Blocks — chosen because they are the structurally fragile ones. Component-level
rather than full-page, so a change to one card does not churn the other three.

Three rules that are load-bearing:

- **Baselines are generated in CI, never locally.** They are pixel comparisons,
  so they are only valid for the environment that produced them; a baseline made
  on a laptop fails on the runner over font antialiasing alone, and a check that
  cries wolf is a check people learn to ignore. Add the
  `update-visual-baselines` label to a PR and `visual-baselines.yml` commits the
  new baselines for you — **or, if that label does not exist in the repository
  (it did not as of v1.8.0), run the same workflow from the Actions tab with
  *Run workflow* against your branch.** The job handles both triggers and
  pushes to the same place; the label is the convenience, not the mechanism.
- **`updateSnapshots: 'none'`.** Playwright's default is `'missing'`, which
  *writes* an absent baseline and passes. Since CI never commits what it writes,
  the baseline would be regenerated on every run and compared against itself —
  permanently green, permanently vacuous. A missing baseline must fail.
- **The clock is frozen** at a fixed instant, and the block fixtures derive from
  that same instant. Three things in these cards read `Date.now()`: the Power
  Law fair value (a function of days since genesis, so it drifts *every day*),
  the "N min ago" on the latest block, and the header's "Updated HH:MM". Without
  freezing, the Cycle Indicators baseline goes stale overnight, every night.

> If the churn ever outweighs the value, deleting `visual.spec.js` and its
> baselines is a legitimate outcome — that tradeoff was made with eyes open when
> this shipped, and #18 says so explicitly.

> **After running `visual-baselines.yml`, the PR cannot turn green by itself.**
> Its commit is pushed with the default `GITHUB_TOKEN`, and GitHub deliberately
> refuses to let a workflow's own push start further workflows — the recursion
> guard. The runs are still *created* against the new head, but they sit in
> **`action_required`** waiting for an approval that nothing will give, so both
> required checks stay pending forever and the PR looks stuck for no stated
> reason.
>
> **Close the PR and reopen it.** That fires `pull_request: reopened` as a human
> action against the current head, and CI and Playwright run normally. An empty
> commit works too and is worse — it puts a junk commit in the history of every
> design change. This is a property of the workflow, not of any one PR: it will
> happen every time the baselines are regenerated.

### Styling

Tailwind CSS v4 via the `@tailwindcss/vite` plugin — **not** PostCSS. The import
in `src/index.css` is `@import "tailwindcss"`. No `tailwind.config.js` needed.

**Every colour in this app is a role, not a hue**, and that rule is enforced:
`palette.test.js` fails if any `.js` or `.jsx` under `src/` contains a Tailwind
palette class (`text-gray-400`, `bg-orange-500`, `text-white`, …) or a raw hex.
Use `bg-surface`, `text-quiet`, `text-accent`, `text-up`. The names are listed in
`src/lib/palette.js`; Tailwind generates a utility for each one automatically.

The token set is declared **twice on purpose** and pinned by a test across the
pair:

- **`src/lib/palette.js` is the source of truth.** Change colours here.
- **`src/index.css` mirrors it** — `@theme` holds the light values, and a
  `.dark {}` block below overrides them. That block is unlayered while Tailwind
  emits `@theme` into `@layer theme`, so it wins; it is also later in source
  order, so it would win anyway.

The duplication is not avoidable. Tailwind can only read a stylesheet, and three
consumers can only read JavaScript — `ShareCanvas` (rasterised by html2canvas),
`api/lib/ogView.js` (Satori, in a serverless function that never loads the CSS)
and `scripts/generate-icons.mjs` (node). Before this there were six independent
constant blocks, which is how the app shipped two different brand oranges.

For a value in JS — recharts takes colours as props, not classes:

```js
import { PALETTE } from '../lib/palette.js'
import useTheme from '../hooks/useTheme.js'
const { theme } = useTheme()
<Line stroke={PALETTE[theme].accent} />   // PALETTE[theme]['line-strong'] if hyphenated
```

**Band scales live in `src/lib/scales.js`**, never in the component. Each band
carries its Tailwind class *and* its palette token, because the cards want a
class and the canvas wants a hex, and a test asserts the two agree — a composed
`text-${token}` is invisible to Tailwind's scanner, so the utility is never
generated and the element silently inherits its parent's colour.

**Theming.** `<html>` carries `.dark` or not; `useTheme` owns it after mount and
the inline boot script in `index.html` applies it before the first paint. No
stored preference means follow the OS. A `dark:` variant exists via
`@custom-variant` for the rare case a token cannot express something, but
reaching for it usually means a token is missing.

**When adding a colour**: add the token to `palette.js` *and* both blocks in
`index.css`, and let `palette.test.js` tell you whether it clears AA on every
surface it will sit on — in both themes. It checks `ground`, `surface` and
`raised`, and `raised` is the one that catches things.

**Type is a role too, and it lives in `src/lib/typography.js`.** The `@theme`
block declares `--font-sans` and `--font-mono` mirroring that module, for the
same reason the palette is mirrored — `ShareCanvas` and `ShareModal` are styled
inline and can only read JavaScript. Do not write a font stack anywhere else;
`typography.test.js` fails the build if you do. Swapping to a display face is
that module plus its mirror, but it comes with two requirements the module
states: the face must carry real tabular figures, and it must be supplied to
Satori *and* html2canvas in the same change or the preview card and the share
image drift away from the site silently.

**Any figure that changes without a page reload gets `tabular-nums`.**
Proportional digits are different widths, so a price ticking 100,111 → 100,888
reflows its row on every tick. `typography.test.js` holds the eleven cards that
render live figures to this. Note that **the visual baselines cannot see it** —
`font-variant-numeric` needs a `tnum` table and the CI container's fallback face
has none, so the property is asserted rather than the glyph widths.

**Icons are a scale, not a drawing decision.** `src/lib/icons.js` holds every
one of them on a single 24×24 viewBox at a single stroke weight, and
`Icon.jsx` is the only file in `src/` that writes an `<svg>` — `icons.test.js`
fails the build if a second one appears. A call site picks a name and one of
three sizes (`sm` 12, `md` 14, `lg` 16); it does not pick a weight, a box or a
pixel value, because those varying independently is what produced five sizes and
five stroke weights across thirteen hand-written elements.

**Do not draw a control with a text glyph.** `✕`, `▾`, `▲` and `▼` resolve in
whatever font the device supplies, which is the tofu risk v1.8.1 removed from
the app mark; the same test scans for them. `×` is fine — it is the Mayer
Multiple's unit, a multiplication sign in a number rather than a picture.

**Adding an icon** means a `[tag, attrs]` entry in `ICON_PATHS` drawn on the 24
box. The registry is held to being neither short nor long: a name no call site
asks for fails, and so does a name asked for that is not defined. `api/lib/ogView.js`
is the one surface that deliberately does not follow, for the same reason it does
not follow the typography — Satori draws it and its arrows are already inside the
character set `ogImage.test.js` pins.

**The round header button is `ICON_BUTTON`**, and `ICON_BUTTON_LABELLED` for the
two that grow a text label at `md:`. It was written out four times before. Colour
is not in either constant and should stay out — `text-quiet` for settings,
`text-accent` for actions is a real distinction, not drift.

**Focus is not a per-control decision.** `index.css` carries one blanket
`:focus-visible` rule and it is **unlayered**, so a Tailwind utility cannot beat
it — do not add `outline-none`, `focus:outline-none` or a `focus:ring-*` of your
own, and `palette.test.js` fails the build if you do. The rule was measured, and
the measurement has a trap: with a control carrying `outline-none`, the same
rule inside `@layer base` paints **nothing**, while `@layer utilities` happens
to paint the ring only because the block sits later in the file than the
`@import`. Unlayered is the version that does not depend on where it is written.

**Headings are structure, not size.** A card's title is an `<h2>`; a titled
section inside a card is an `<h3>`; individual stat labels stay `<p>`. Tailwind
preflight resets heading `font-size` and `font-weight` to inherit, so the tag
carries no appearance and changing it moves no pixels.
`cardHeadings.test.jsx` renders every titled card and separately scans
`src/components/` for anything with a `rounded-2xl bg-surface` root that has no
`<h2>` — which is what catches the next card written by copying an older one.

### Database (Supabase Postgres)

Schema lives in `supabase/migrations/`. Both tables have RLS enabled; re-run the
security advisors after any change and expect zero lints.

| Table | Purpose | Anon access |
|---|---|---|
| `donors` | Names submitted via the donation card | `SELECT` where `approved = true`; `INSERT` only with `approved = false`. No update or delete. |
| `metric_snapshots` | One row per UTC day of dashboard metrics (`jsonb`), written by the Actions snapshot job | `SELECT` only. Writes are service-role. |
| `push_subscriptions` | One row per browser opted in to Web Push, plus the alert rules the evaluator reads | **`INSERT`**; `UPDATE` on the `rules` column only; `SELECT` on the `secret_hash` column only. Both reads and writes are scoped by RLS to the row whose `secret_hash` matches the request's `x-push-secret` header, so a caller sees and changes at most its own row. `endpoint`, `p256dh` and `auth` are readable by nobody (a push endpoint is a capability *and* a durable browser identifier), and there is deliberately no `DELETE` — see below. |
| `push_evaluate_log` | One row per push-evaluator cron tick, holding the `pg_net` request id so the real HTTP status can be joined back | **None.** All grants revoked, plus an explicit `for all … using (false) with check (false)` deny policy; `service_role` (via `BYPASSRLS`) and the cron job's `SECURITY DEFINER` function are the entire access list. |

> **Grants and RLS are two different gates, and `push_subscriptions` is where
> that stopped being academic.** RLS decides *which rows*; the table grant
> decides *which verbs* — and **`TRUNCATE` bypasses RLS entirely**, while
> Supabase's default grants hand `anon` `TRUNCATE` on every table in `public`.
> Measured against the new table with RLS on and only an INSERT policy: every
> `DELETE` and `UPDATE` correctly affected 0 rows, and `truncate` emptied it.
> PostgREST maps no HTTP verb to `TRUNCATE`, so none of this was reachable from
> the deployed app — but that is a property of this version of PostgREST, not
> an access control. All three tables now hold exactly the verbs the app uses
> (`20260808100100_narrow_anon_grants.sql` for the two older ones). When adding
> a table, revoke first and grant back.
>
> **PostgREST refuses an unfiltered `UPDATE` or `DELETE` outright** — `400`,
> `21000`, *"UPDATE requires a WHERE clause"* — which is a different gate again
> from grants and RLS, and it sits *in front* of both: the statement never
> reaches Postgres, so no policy of ours is consulted. v1.7.8's rules sync was
> built on an unfiltered `UPDATE` scoped purely by RLS, verified with
> `set role anon` in SQL where there is no PostgREST, and it therefore failed on
> every real request for eight versions. **Verify a PostgREST path over HTTP,
> not in SQL** — they are not the same code path.
>
> The fix (`20260809170000`) filters on `secret_hash`, which forces two further
> grants that are worth understanding before adding any similar write. A `WHERE`
> clause needs `SELECT` privilege on the column it names, so there is now a
> **column-level** `grant select (secret_hash)` — never on the table, because a
> readable `endpoint` column is an enumeration oracle. And **an `UPDATE` with a
> `WHERE` clause has to read the rows it filters, so `SELECT` *policies* apply
> to it too**: with none, the filtered write matched zero rows even with a
> correct secret (`204`, `content-range: */0`). Hence a `SELECT` policy scoped
> to the same secret. Measured over HTTP afterwards: correct secret → 1 row;
> no header → 0; another row's hash → 0; `select=endpoint` → `42501`;
> `select=secret_hash` with no secret → `[]`.
>
> **`push_subscriptions` has no `DELETE` policy on purpose.** A policy permissive
> enough to erase your own row is permissive enough to erase everybody's, and
> the browser has no need of one. Unsubscribing happens in the browser:
> `subscription.unsubscribe()` invalidates the endpoint at the push service, so
> nothing can be delivered to it whatever the row says, and the sender reaps it
> on the first `410 Gone` — the same path that handles a browser somebody
> uninstalled. That reaping is live as of v1.7.13, in `api/push-evaluate.js`,
> and it is deliberately narrow: only `404` and `410` destroy a row, because a
> `403` means the VAPID signature was rejected and reaping on it would empty the
> table the first time somebody pasted the wrong key.

`metric_snapshots` is keyed by a generated `captured_on` date with a unique
index, so the job upserts and re-runs are idempotent. The first read of it lands
in v1.6.5: `api/chain-data.js` serves its stored MVRV when BGeometrics does not
answer. The second lands in v1.6.9: `useVibeHistory` replays the last 30 rows
into the Vibe Score sparkline, which is the first read of this table from the
browser.

> A Supabase Database Webhook (`new_donor_notification`) POSTs each new donor row
> to a Make.com automation. That URL is a capability URL and is deliberately
> **not** committed — the baseline migration documents it with a placeholder.
> Manage it from the Supabase dashboard, not from the repo.

### Scheduled jobs

| Job | Where | Cadence |
|---|---|---|
| Daily metrics snapshot | GitHub Actions (`snapshot.yml`) | 06:17 UTC, plus `workflow_dispatch` |
| Push alert evaluation | `pg_cron` → `net.http_post` → `/api/push-evaluate` | every 5 minutes |
| `push_evaluate_log` trim | `pg_cron` | 04:17 UTC daily, keeps 7 days |

The push evaluator is scheduled by `pg_cron` rather than by Actions or Vercel
Cron because neither can hold a five-minute schedule: `snapshot.yml` asks for
06:17 UTC and its scheduled runs start around 09:10, and Vercel Hobby crons run
once a day. Its URL and bearer token live in the Supabase Vault, not in the
migration — see `20260809120000_schedule_push_evaluate.sql`.

> **`net.http_post` reports that a request was *queued*, not what came back**,
> which is how a `donor-email-worker` job ran every minute for months against an
> edge function that never existed: every response was a 404 and pg_cron logged
> "succeeded" on all of them. It was removed in
> `20260805063000_remove_orphaned_donor_email_worker.sql`, and the evaluator is
> written around that lesson — it records each request id in
> `push_evaluate_log`, so the real status codes are one join away:
>
> ```sql
> select l.fired_at, r.status_code, r.content
> from public.push_evaluate_log l
> left join net._http_response r on r.id = l.request_id
> order by l.fired_at desc limit 20;
> ```
>
> pg_net prunes `net._http_response` after a few hours, so a null `status_code`
> on an older row means the response expired, not that nothing arrived. The
> route itself never answers 200 when it is misconfigured — it answers 503, so a
> missing environment variable is visible in that column rather than silent.

Donor notifications do **not** depend on it. They come from the
`new_donor_notification` trigger on `donors`, which POSTs to a Make.com webhook.
